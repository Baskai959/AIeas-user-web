## REST DTO 建议

新的 `default.openapi.json` 目前多数 `data` schema 为空对象。为避免前后端理解偏差，建议补齐以下响应模型。

`LiveRoom`：

```ts
{
  id: string
  title: string
  merchantId?: string
  merchantName: string
  status: 'LIVE' | 'UPCOMING' | 'ENDED'
  videoSource: 'recorded' | 'digitalHuman'
  coverUrl?: string
  videoUrl?: string
  digitalHuman?: {
    idleVideoUrl: string
    speakingVideoUrl: string
    ttsWsUrl?: string
  }
  onlineCount: number
  watcherCount: number
  likeCount?: number
  activeAuctionId?: string
  liveSessionId?: number
  startedAt?: string
  endedAt?: string
}
```

`LiveRoomLot`：

```ts
{
  id: string
  auctionId: string
  roomId: string
  title: string
  subtitle?: string
  description?: string
  imageUrl?: string
  imageUrls?: string[]
  status: 'UPCOMING' | 'READY' | 'WARMING_UP' | 'RUNNING' | 'EXTENDED' | 'HAMMER_PENDING' | 'CLOSED_WON' | 'CLOSED_FAILED' | 'SETTLED' | 'CANCELED'
  startPrice: number
  currentPrice: number
  finalPrice?: number
  leaderBidderId?: string
  startTsMs?: number
  endTsMs: number
  ruleSnapshot?: {
    startPrice?: number
    minIncrement?: number

    antiSnipeSec?: number
    extendSec?: number

  depositAmount?: number
  participantCount?: number
  bidCount?: number
  sortOrder?: number

```

用户端直播间竞拍清单使用 `LiveRoomLot.subtitle` 作为商品简介；`LiveRoomLot.description` 保留给拍品详情页展示详细描述。远程数据归一化时前端优先读取 `subtitle`，并继续以 `brand` 作为历史字段兜底。

`LiveRoomFootprint`：

```ts
  viewedAt: string
}
```

## 接口修正和追加

1. `GET /api/v1/orders/mine` 建议增加 `auctionId` 查询参数。

   用户端结果页 `/result/:auctionId` 需要从成交拍品定位当前用户订单。新 OpenAPI 仅有 `winnerId`、`sellerId`、`status`、`payStatus`，不适合用户端按拍品查自己的结果。当前前端已按 `auctionId` 参数设计：

   ```text
   GET /api/v1/orders/mine?limit=20&offset=0&auctionId={auctionId}
   ```

   直播间拍品详情页的 `查看订单` 动作也复用该能力：前端会根据已成交拍品的 `auctionId` 找到当前用户订单，并跳转 `/orders?tab=...&orderId=...` 高亮对应记录；如果订单尚未返回，则只显示禁用的“订单生成中”，不伪造订单 ID。

2. WebSocket 文档建议补齐 `snapshot` 或明确 REST 快照恢复。

   `拍卖客户端实时交互方案.md` 要求客户端断线或 `room.snapshot_required` 后拉快照，但 `live-room-websocket.openapi.json` 没有 `snapshot` 事件。建议二选一：

   - 增加 `snapshot` 事件，payload 包含 `auctionId/status/currentPrice/leaderBidderId/endTsMs/serverTsMs/seq/ranking`。
   - 明确 `room.snapshot_required` 后客户端调用 `GET /api/v1/auctions/{id}/state`，如需排行榜则追加 REST snapshot 接口。

   当前前端按第二种方向实现。

3. WebSocket 文档建议补齐 `gateway.draining` 事件。

   用户端真实 WebSocket 客户端已支持 Gateway 优雅下线迁移：收到 `gateway.draining` 后，按 `payload.retryAfterMs` 作为最小等待时间主动关闭当前连接，并在重连时继续携带持久化 `lastSeq`。建议 `live-room-websocket.openapi.json` 将该事件补入 type 枚举，payload 至少包含：

   ```ts
   {
     retryAfterMs: number
   }
   ```

   该事件不改变业务状态，只用于连接迁移；客户端不应清空 `lastSeq`，也不应假设会回到同一 Gateway。

4. `BidPlacePayload` 建议移除前端侧 `idempotencyKey` 字段。

   新 WS schema 同时包含 `requestId` 和 `idempotencyKey`。为保持 envelope 简洁，前端只发送：

   ```ts
   {
     auctionId: string
     price: number
     requestId: string
   }
   ```

   后端可将 `requestId` 作为 WS 出价幂等键；如后端坚持 `idempotencyKey`，建议在服务端由 `requestId` 派生，不要求用户端重复提交两个字段。

5. 价格展示规则需固定到接口语义。

   - 无出价：展示 `起拍价`。
   - 已有人出价且未终态：展示 `当前最高价`。
   - `HAMMER_PENDING`、`CLOSED_WON`、`SETTLED`：展示 `落槌价`。
   - `CLOSED_FAILED`：展示 `起拍价` 或 `流拍` 状态，不展示成交价。

6. 直播间拍品列表需要区分 `finalPrice` 与 `currentPrice`。

   已成交拍品如果只返回 `currentPrice`，用户端仍可展示；但为了避免语义混淆，建议后端终态返回 `finalPrice`。

7. 直播间拍品详情建议返回 `imageUrls` 图集字段。

   用户端拍品详情页支持 1-5 张拍品大图循环切换和全屏看图。建议 `GET /api/v1/live-rooms/{id}/lots` 与后续独立拍品详情接口均返回：

   ```ts
   {
     imageUrl?: string
     imageUrls?: string[]
   }
   ```

   `imageUrl` 继续作为列表封面和单图兜底；`imageUrls` 用于详情图集，前端最多使用前 5 张。若两者都缺失，用户端显示本地占位图，不猜测图片地址。

8. 直播间视频源需要由 REST 明确配置。

   用户端不再允许用户手动切换实景/数字人视频源，必须由商家配置并通过 `LiveRoom.videoSource` 返回：

   ```ts
   {
     videoSource: 'recorded',
     videoUrl: string
   }
   ```

   或：

   ```ts
   {
     videoSource: 'digitalHuman',
     digitalHuman: {
       idleVideoUrl: string
       speakingVideoUrl: string
       ttsWsUrl?: string
     }
   }
   ```

   数字人本地 Demo 素材为 `/media/AI_Presenter_Silent.mp4` 和 `/media/AI_Presenter_Speaking.mp4`。`ttsWsUrl` 是商家/服务端驱动播报的音频流配置字段；用户端点击直播间统一声音开关后会连接该 TTS WebSocket，并按 `audio_start`、二进制 PCM chunk、`audio_end` 驱动 Web Audio 播放和说话/待机视频层切换。用户端不显示播报文本、发送播报、停止、重连等控制元素，也不向 TTS 服务提交播报文本。移动端浏览器内联播放、防止 X5/系统播放器接管、禁用画中画和远程播放入口均由前端 `<video>` 属性处理，不新增后端接口字段。

9. 直播间评论需要补齐 WebSocket 事件。

   用户端评论不走 REST，直接复用直播间 WebSocket envelope：

   ```ts
   { type: 'chat.send', requestId, payload: { roomId, content, clientMessageId } }
   { type: 'chat.ack', requestId, ack: true, payload: { roomId, clientMessageId, messageId, createdAt } }
   { type: 'chat.message', seq, payload: { id, roomId, userId, nickname, avatarUrl?, content, createdAt, clientMessageId? } }
   { type: 'chat.error', requestId, payload: { roomId, clientMessageId?, message } }
   ```

   `chat.message` 建议带 `seq`，这样评论与出价、倒计时等事件共用同一套去重和恢复策略。`clientMessageId` 建议在服务端广播当前用户消息时回传，用于前端合并本地乐观消息和服务端确认消息。

10. 订单需要补齐履约状态。

   “我的”页已经从旧的四类竞拍记录调整为 `全部 / 待竞价 / 待支付 / 待发货 / 待收货 / 已完成`。其中 `待发货 / 待收货 / 已完成` 不能由支付状态可靠推断，订单对象需要返回：

   ```ts
   fulfillmentStatus?: 'UNSHIPPED' | 'SHIPPED' | 'RECEIVED'
   shippedAt?: string
   receivedAt?: string
   ```

   `GET /api/v1/orders/mine`、`GET /api/v1/orders/{id}`、`POST /api/v1/orders/{id}/pay`、`POST /api/v1/orders/{id}/receive` 以及 `GET /api/v1/auction-participations/mine` 内嵌订单均应使用同一 `Order` DTO。远程接口缺少 `fulfillmentStatus` 时，前端不会猜测发货/收货状态，该记录只进入 `全部`。

   用户确认收货建议新增：

   ```text
   POST /api/v1/orders/{id}/receive
   ```

   约束：仅买家本人可调用；订单应已支付且当前 `fulfillmentStatus=SHIPPED`；成功后返回更新后的 `Order`，其中 `fulfillmentStatus=RECEIVED`，`receivedAt` 为服务端时间。前端会在 `/orders?tab=pendingReceipt` 调用该接口，并用返回 DTO 立即更新本地订单缓存，使记录进入 `completed` 分组。

11. 用户直播间关注和浏览足迹不定义后端接口。

   关注和足迹均为用户端纯前端演示能力，持久化在本地 `aieas-user-live-activity` store 中，不调用 REST 或 WebSocket。关注对象按直播间维度，不按商家维度；足迹分为直播间足迹和拍品足迹：直播间足迹只在用户进入完整直播间 `/live/:roomId` 时记录，首页直播推荐流预览不记为足迹；拍品足迹在用户进入 `/product/:lotId` 并成功加载拍品后记录。同一直播间或同一拍品重复浏览只保留最近一条，两类足迹各自最多保留最近 100 条。

   当前阶段删除关注/足迹相关后端接口建议，避免与“纯前端持久化演示”的产品边界冲突。后续若确认需要跨设备同步，再重新设计用户行为接口，不保留旧草案路径兼容层。

12. `LiveRoomLot.ruleSnapshot` 建议补齐最小出价间隔字段。
   快速出价弹层需要限制同一用户连续出价的最小间隔。当前前端 Demo 默认使用 `1000ms`，真实联调时建议后端在拍品规则快照中返回：

   ```ts
   ruleSnapshot: {
     minIncrement?: number
     ceilingPrice?: number
     minBidIntervalMs?: number
     antiSnipeSec?: number
     extendSec?: number
   }
   ```

   `minBidIntervalMs` 的单位为毫秒。若远程接口缺少该字段，前端按默认值 `1000` 处理并在 UI 内给出冷却提示；后续真实生产规则应以后端返回值为准。

13. `LiveRoom.likeCount` 建议作为直播间顶部 UI 字段返回。

   用户端顶部商家胶囊需要展示直播间点赞数。`likeCount` 作为后端返回的基础点赞数；若接口缺失则用户端按 0 处理，本地 Demo 直播间也统一默认 0。用户端底部点赞按钮当前是纯前端演示能力，只会按 `roomId` 在本地累加演示点赞增量，并与 `likeCount` 相加显示，不调用 REST 或 WebSocket。建议 `GET /api/v1/live-rooms` 与 `GET /api/v1/live-rooms/{id}` 均返回：

   ```ts
   {
     likeCount?: number
   }
   ```

14. `ranking.updated` 建议补齐当前用户排名项。

   直播间右侧实时排行榜固定展示前 8 名槽位，并在底部固定展示当前用户信息。如果当前用户不在前 8 名，但前端拿得到当前用户的 `RankingItem`，则会按同一结构显示当前用户；真实后端如果只推 top8，前端无法准确展示当前用户名次，也不会伪造排名。

   建议 `RankingItem` 结构补齐可选头像字段，便于用户端展示头像：

   ```ts
   {
     rank: number
     bidderId: string
     nicknameMask: string
     avatarUrl?: string
     price: number
     bidTsMs: number
   }
   ```

   建议后端在 `ranking.updated` 中二选一：

   ```ts
   {
     auctionId: string
     items: RankingItem[] // 至少前 8 名，并包含当前用户排名项
   }
   ```

   或：

   ```ts
   {
     auctionId: string
     items: RankingItem[] // 前 8 名
     currentUserItem?: RankingItem
   }
   ```

   `currentUserItem` 必须使用与 `items` 完全一致的 `RankingItem` 结构，不增加旧字段或单独格式。若后端采用 `currentUserItem`，前端后续可直接按该字段渲染，不需要保留旧排名兼容层。`ranking.updated` 应配合 `bid.accepted` 事件发送，前端会用最近一次 `bid.accepted.bidderId` 驱动排名变化动画；如果后端无法保证事件顺序，建议在 `ranking.updated` 中直接提供最近出价人的 `bidderId`。

## 当前前端策略

- 默认使用本地 Demo 数据，不默认请求 Apifox Mock 或真实后端。
- 真实 REST 联调通过 `VITE_API_MODE=remote` 和 `VITE_API_BASE_URL` 开启。
- 真实 WS 联调通过 `VITE_REALTIME_MODE=websocket` 和 `VITE_WS_URL` 开启。
- 出价金额字段统一为 `price`，单位为分。
- 直播间视频源字段统一为 `videoSource`，不保留用户侧手动切换或旧数字人环境变量兜底。
- 直播间顶部点赞数读取 `LiveRoom.likeCount` 作为基础值；缺失时按 0 处理，本地 Demo 直播间也统一默认 0。底部点赞按钮产生的本地演示点赞增量只保存在前端并叠加显示，不作为正式接口字段或后端统计依据。
- 数字人播报不作为观看端用户可操作能力暴露；后端如提供音频流，应由 `digitalHuman.ttsWsUrl` 或联调环境变量配置，并由商家配置或服务端事件驱动，不要求用户端提交播报文本。
- 评论发送和接收统一走 `chat.*` WebSocket 事件。
- 实时排行榜仅在当前直播间存在 `RUNNING / EXTENDED` 拍品时显示。数据使用 `ranking.updated.items`，固定渲染前 8 名槽位和底部当前用户行；当前用户不在前 8 名时只在数据中存在对应 `RankingItem` 的情况下显示其真实排名，前端不伪造当前用户名次。
- `auction.closed` 表示当前拍品竞拍结束，前端只更新直播间内拍品状态，不自动跳转出直播间。
- 快速出价最小间隔优先读取 `LiveRoomLot.ruleSnapshot.minBidIntervalMs`，缺失时使用前端默认值 `1000ms`。
- “我的”页状态由保证金、拍品状态、订单支付状态和 `Order.fulfillmentStatus` 派生，不接收旧 `waiting / bidding / ended / won` 记录状态。
- 关注和足迹使用前端本地持久化，不定义真实后端接口；后续如需跨设备同步，应重新设计用户行为接口，不保留旧“提醒/收藏”入口语义。
- 不接收或发送旧 `bidPrice` 字段。
- 不保留旧 `/api/v1/auctions` 列表/详情/我的拍品接口兼容层。

## 2026-05-30 搜索、商家与分类接口缺口

本轮用户端新增首页、全局搜索、商家详情和商品详情。当前后端 OpenAPI 尚未覆盖搜索、商家主页、分类列表和独立拍品详情，因此首版前端使用本地 Demo 聚合数据完成演示，不新增真实后端依赖。

前端服务层已预留以下能力：

```ts
listCategories(): Promise<PageResult<Category>>
searchLots(options: SearchLotsOptions): Promise<PageResult<LiveRoomLot>>
searchLiveRooms(options: SearchLiveRoomsOptions): Promise<PageResult<LiveRoom>>
searchMerchants(options: SearchMerchantsOptions): Promise<PageResult<Merchant>>
getMerchant(id: string): Promise<Merchant>
getLot(id: string): Promise<LiveRoomLot>
```

建议后端后续补齐 REST：

- `GET /api/v1/categories?limit=&offset=`
- `GET /api/v1/search/lots?keyword=&sort=&status=&categoryId=&merchantId=&limit=&offset=`
- `GET /api/v1/search/live-rooms?keyword=&sort=&status=&limit=&offset=`
- `GET /api/v1/search/merchants?keyword=&limit=&offset=`
- `GET /api/v1/merchants/{id}`
- `GET /api/v1/lots/{id}`

建议 DTO：

`Category`：
```ts
{
  id: string
  name: string
  iconName?: string
}
```

`Merchant`：
```ts
{
  id: string
  name: string
  avatarUrl?: string
  description?: string
  followerCount: number
  fansCount?: number
  rating?: number
  liveRoomId?: string
  location?: string
}
```

`LiveRoomLot` 需补齐搜索和商家页所需字段：
```ts
{
  merchantId?: string
  categoryId?: string
  publishedAt?: string
  imageUrl?: string
  imageUrls?: string[]
}
```

排序和状态枚举建议：

- 拍品排序：`default`、`auctionTime`、`publishedAt`、`priceAsc`、`priceDesc`
- 拍品状态筛选：`running`、`ended`、`failed`、`upcoming`
- 直播排序：`default`、`lotCount`、`gmv`、`watchers`
- 直播状态筛选：`ended`、`live`、`upcoming`

当前项目处于开发阶段，新增接口接入时不保留本地字段别名兼容层；后端字段应直接与上述前端模型对齐。

## 2026-05-30 分类详情、发现流与我的页接口缺口

本轮前端新增分类详情、发现推荐流、个人中心、头像裁剪和昵称设置。当前仍以本地 Demo 数据完成演示，不新增真实后端依赖。为后续联调，建议后端补齐以下 REST：

- `GET /api/v1/users/me/profile`
- `PATCH /api/v1/users/me/profile`

头像上传建议由 `POST /api/v1/users/me/avatar` 接收裁剪后的图片文件或 base64，并返回更新后的 `UserProfile`。前端当前在本地使用 canvas 生成 256 x 256 圆形裁剪结果；真实接入时建议后端返回可长期访问的 `avatarUrl`，前端不保存文件二进制。

`UserAuctionRecord` 建议 DTO：

```ts
{
```

“我的”页状态不再由后端返回 `waiting / bidding / ended / won`。前端统一派生 `MyAuctionTabKey`：

```ts
type MyAuctionTabKey = 'all' | 'pendingBid' | 'pendingPay' | 'pendingShipment' | 'pendingReceipt' | 'completed'
```

分组语义：

- `all`：所有缴纳过保证金的记录，定义为 `depositStatus` 表示已缴纳/冻结/释放/抵扣，或 `depositAmount > 0`。
- `pendingBid`：已缴保证金，拍品状态为 `UPCOMING / READY / WARMING_UP / RUNNING / EXTENDED`，且尚未产生订单。
- `pendingPay`：存在订单，且 `payStatus=UNPAID` 或 `status=PENDING_PAY`。
- `pendingShipment`：订单已支付，且 `fulfillmentStatus=UNSHIPPED`。
- `pendingReceipt`：订单 `fulfillmentStatus=SHIPPED`。
- `completed`：订单 `fulfillmentStatus=RECEIVED`。
- 已缴保证金但竞拍失败、流拍或缺少订单履约状态的记录只进入 `all`，不伪造发货/收货状态。

发现页当前复用 `GET /api/v1/search/live-rooms?status=live&sort=watchers`。如果后续需要推荐策略，建议新增：

```text
GET /api/v1/discover/live-rooms?cursor=&limit=
```

返回结构仍使用 `PageResult<LiveRoom>` 或 cursor 分页结果，避免前端为推荐流另建一套直播间 DTO。

分类详情继续复用 `GET /api/v1/search/lots?categoryId=...`。该接口需要稳定支持 `sort`、`status`、`categoryId`，以保持首页分类、分类页和搜索拍品页的筛选逻辑一致。
