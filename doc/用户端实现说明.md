# 用户端实现说明

## 当前范围

本项目实现直播竞拍全栈系统的移动端 H5 用户端。当前版本以“可独立演示完整直播竞拍体验”为目标，默认使用本地 Demo 数据和前端 Mock WebSocket。

已实现链路：

- 短视频 App 风格移动端买家登录页，发布版界面默认不展示测试账号或解释性文案，并接入登录守卫回跳，注册和忘记密码入口仅预留
- 首页直播推荐流，支持移动端上下滑动、首尾循环切换和 PC 拖拽/滚轮模拟
- 发现页拍品列表，标题和筛选区支持随列表滚动收起，并可在用户向下滑动/下拉列表时重新呼出
- 全屏直播间与固定视频模拟；从首页直播预览进入时，同源视频会承接预览播放进度
- REST 配置的直播间视频源：实景视频或数字人视频
- 数字人待机/说话双视频层，用户端不暴露播报控制
- 直播间评论展示、评论输入、评论开关和评论 WebSocket 事件
- 右下角竞拍清单入口
- 直播间商品列表 70% 屏高底部抽屉，内部可滚动，本地 Demo 直播间默认提供 10 件拍品，当前竞拍中的拍品置顶显示，列表项名称下方仅展示 `LiveRoomLot.subtitle` 商品简介
- 拍品详情 75% 屏高底部弹层
- 报名与保证金模拟冻结
- 手动出价、步进加价、本地基础校验
- 当前最高价、起拍价、落槌价按状态展示
- 实时在线人数、排行榜、出价 ACK、领先、延时、成交、场次结束事件
- 基于实时事件派生的全局竞价氛围弹窗：领先、被超越、竞拍延时、竞拍结束、竞拍成功
- 基于当前拍品 `endTsMs` 派生的最后 10 秒倒计时提醒：复用全局竞价氛围弹窗，优先级低于其他竞拍提醒，最后 3 秒强化动效
- 成交结果、模拟支付、历史订单
- “我的”页关注/足迹入口、我的订单入口、关注列表、直播间/拍品足迹列表、订单列表页和设置页退出登录

## 技术选型

- React 18 + TypeScript + Vite
- Ant Design Mobile 作为移动端 UI 基础组件
- Zustand 管理会话状态
- TanStack Query 管理 REST 数据请求
- React Router 管理页面路由、深链和登录守卫
- 原生 WebSocket 抽象管理实时通信

旧版用户端需求文档曾同时提到 `vant / antd-mobile / Tailwind` 任选。由于当前项目采用 React，Vant 属于 Vue 生态，本实现继续使用 Ant Design Mobile，不引入 Vant。

默认 API 客户端使用本地 Demo 数据，不再默认访问 Apifox REST Mock。真实联调时推荐使用 Vite 同源反代，浏览器访问前端同源的 `/api` 和 `/ws`，由 dev server 转发到后端：

```env
VITE_API_MODE=remote
VITE_API_BASE_URL=
VITE_REALTIME_MODE=websocket
VITE_WS_URL=
VITE_DEV_PROXY_TARGET=http://127.0.0.1:8888
```

若不使用反代，也可显式设置 `VITE_API_BASE_URL` 和 `VITE_WS_URL` 为后端地址，但后端必须允许前端页面来源的 CORS 预检和正式请求。

真实联调模式下，直播间页面等待 `LiveRoom`、拍品清单和统计接口返回时，只使用不含商家 ID 的轻量 loading 占位与空拍品列表；真实房间数据返回后再按后端 `merchantId` 请求商家详情。这样可以避免本地 Demo 默认房间回退到 `merchant_01` 后污染真实后端请求日志。

## 实时通信

实时通信按原生 WebSocket envelope：

```ts
{
  type: string
  requestId?: string
  seq?: number
  ack?: boolean
  liveSessionId?: number
  payload: Record<string, unknown>
}
```

当前默认 `MockRealtimeClient`，覆盖：

- `room.subscribed`
- `room.online`
- `heartbeat.ack`
- `bid.ack`
- `bid.accepted`
- `bid.rejected`
- `ranking.updated`
- `room.snapshot_required`
- `timer.extended`
- `auction.closed`
- `live_session.ended`
- `chat.ack`
- `chat.message`
- `chat.error`

为覆盖实时排行榜位次变更动画，本地 `MockRealtimeClient` 在当前用户首次出价并成为领先者后，会自动模拟一次其他买家加价，并按现有 `bid.accepted -> ranking.updated` 顺序推送事件。该自动竞争出价每个 mock 连接只触发一次，只用于前端 Demo 与回归测试，不新增或修改正式 WebSocket envelope。

本地 Demo 数据中，处于 `RUNNING` 状态的直播间拍品初始剩余倒计时统一为 1 分钟，用于更快触发最后 30 秒光带和最后 10 秒倒计时提醒等演示效果。

客户端维护 `lastSeq`，重复或乱序事件不应用。真实 WS 模式连接：

```text
{VITE_WS_URL}/ws/live-rooms/{roomId}?lastSeq={lastSeq}
```

未显式配置 `VITE_WS_URL` 时，真实 WS 客户端会自动使用当前页面同源的 `ws://{host}` 或 `wss://{host}`，适配 `/ws` 反代。客户端会将游标按 `live-room:{roomId}:lastSeq` 写入 `localStorage`，刷新页面或切换 Gateway 后继续携带该游标。断线后使用 500ms 起步、最大 10s 的指数退避加 jitter 自动重连；收到 `gateway.draining` 时按 `payload.retryAfterMs` 作为最小等待时间主动关闭当前连接并迁移重连。收到 `room.snapshot_required` 时，用户端应以 REST 快照接口刷新状态；当前实现的恢复来源为 `GET /api/v1/auctions/{id}/state`。

评论也走同一条直播间 WebSocket：

```ts
{ type: 'chat.send', requestId, payload: { roomId, content, clientMessageId } }
{ type: 'chat.ack', requestId, ack: true, payload: { roomId, clientMessageId, messageId, createdAt } }
{ type: 'chat.message', seq, payload: { id, roomId, userId, nickname, avatarUrl?, content, createdAt, clientMessageId? } }
{ type: 'chat.error', requestId, payload: { roomId, clientMessageId?, message } }
```

## 数字人视频源

直播间视频源由后端/商家配置决定，用户端不提供实景/数字人手动切换。`LiveRoom.videoSource` 为 `recorded` 时使用 `videoUrl`；为 `digitalHuman` 时使用 `digitalHuman` 配置。前端按 `h5_node_client.mjs` 和本说明的浏览器端视频组织方式实现数字人画面，但用户端不提供播报文本、发送播报、停止、重连等控制元素。直播间顶部的统一声音开关只负责解锁和关闭观看端声音，不承担数字人播报控制。数字人播报应由商家配置或服务端驱动，不由观看端用户触发。从首页直播预览进入正式直播间时，前端会通过 React Router location state 传递预览视频的 `currentTime`；只有直播间和视频源 URL 均匹配时才在正式直播间应用该进度。

- 待机视频和说话视频均为静音 mp4，前端叠加两层视频；接收 `audio_start` 后显示说话视频，播放队列清空后回到待机视频。
- 首页直播预览、直播间实景视频、数字人待机视频和说话视频统一复用移动端内联播放属性：标准 `playsinline`、iOS `webkit-playsinline`、X5 `x5-playsinline` 与 `x5-video-player-type="h5"`，并设置 `x-webkit-airplay="deny"`、禁用原生控件、画中画和远程播放入口，避免手机浏览器把视频资源接管成独立播放窗口后遮挡直播间功能。
- 用户点击统一声音开关后，数字人直播会通过 `digitalHuman.ttsWsUrl` 或 `VITE_TTS_WS_URL` 连接 TTS WebSocket，调用 `DigitalHumanAudioClient.unlockAudio()` 解锁移动端 Web Audio，再按 `audio_start`、二进制 PCM chunk 和播放队列清空事件完成播报音频播放。
- 仓库当前内置数字人视频素材：`public/media/AI_Presenter_Silent.mp4` 和 `public/media/AI_Presenter_Speaking.mp4`。

## 2026-05-31 首页直播流循环方向修正

本轮修正首页直播推荐流的循环动画方向：原实现直接在真实索引间取模，最后一场上滑到第一场时会从尾部位置反向跳回顶部。现在滑轨渲染为“首尾克隆 + 原列表”，最后一场继续上滑时先动画到尾部的第一场克隆项，保持与普通上滑一致的方向；动画结束后再无动画归位到真实第一场。第一场下滑到最后一场也使用同一策略。

- 竞拍清单和拍品详情弹层均使用遮罩淡入与从屏幕底部外侧匀速滑入动画，点击遮罩可关闭。
- 直播间弹层层级高于直播间头部、评论区、当前竞拍拍品小窗和竞拍清单按钮；存在打开中或已打开弹层时隐藏当前竞拍拍品小窗，关闭动画开始后小窗先恢复到 DOM，由遮罩自然遮挡并在动画结束后露出。

- 出价选择器默认取当前价的下一档。当前实现统一读取 `ruleSnapshot.incrementRule`：`type='fixed'` 时使用固定加价额，`type='ladder'` 时按当前价命中价格区间计算加价额。快速出价面板单次最多允许的步数直接使用 `incrementRule.maxBidSteps`，接口缺失时默认使用 3 步；当封顶价与当前价差小于当前加价幅度时，下一档直接落到封顶价。
- 快速出价校验包含封顶价、当前价失效、最小出价间隔和竞拍结束状态。Demo 默认最小出价间隔为 3000ms，真实接口可通过 `ruleSnapshot.minBidIntervalMs` 返回；同一用户上一笔出价一旦被前端确认接受，即使已经成为当前最高价，也必须等待该冷却结束后才能再次提交。冷却提示不会在出价成功后立刻显示，只有用户在冷却期内再次尝试出价时，前端才会给出“出价太频繁”提示并展示剩余倒计时。为防止双击或极短时间内重复点击在按钮禁用前穿透提交，发送 `bid.place` 前还会按 `auctionId` 维度做一次同步提交锁；如果用户在这段本地锁定窗口内再次尝试，前端会立即显示同样的 3000ms 冷却提示，并以本地提示截止时间计算剩余秒数，避免首帧误显示 4s。最近一次本人成功出价时间也会同步写入本地引用，避免成功回包很快时第二次点击读到旧冷却状态。对于 `bid.ack` 这类当前请求的定向成功回包，前端会直接按请求上下文启动冷却，不要求回包额外携带 `bidderId`。封顶价、当前价失效、竞拍结束和本地格式类校验仍会禁用提交或切换按钮状态，但不再作为出价选择器与按钮之间的中间提示展示。
- 提交出价后弹层不立即关闭，而是等待 `bid.ack`、`bid.accepted` 或 `bid.rejected` 反馈。该中间提示位仅保留 `实时连接未就绪，请稍后重试`、`手慢了，当前价已更新，请重新加价`、`当前竞拍太火爆，请稍后再出价`、通用 `出价未通过`，以及前端未命中映射时的后端 `payload.message` 透传。
- 用户停留在快速出价弹层时，如果其他人出价导致当前价更新，已选价格不再高于当前价时确定按钮会禁用；点击加号会基于最新当前价重新加价。
- 用户停留在快速出价弹层时，如果当前商品竞拍结束，弹层倒计时文案变为 `当前商品竞拍已结束`，按钮变为 `该商品拍卖已结束，5s后自动返回直播间` 并倒计时关闭。

`auction.closed` 现在只更新直播间内商品状态，不再自动跳转到成交结果页。成交结果仍可通过结果页路由和后续订单链路进入，避免商品结束事件打断直播间浏览和快速出价关闭动画。

## 2026-06-02 直播间结束态、竞拍小窗收回动画与弹层动效修正

本轮继续修正直播间竞拍结束后的视觉反馈和弹层生命周期：

## 2026-06-02 直播间实时排行榜与弹层并行动效

直播间右侧在关注按钮下方新增吸附侧边的实时排行榜，默认展开。排行榜仅在当前直播间存在 `RUNNING / EXTENDED` 拍品时渲染；没有竞拍中拍品时不显示排行榜面板、展开按钮或收起按钮。排行榜背景使用约 `rgba(0,0,0,0.2)` 的高透明度黑底，不显示“当前出价前8名”等说明文本，以减少对直播画面的干扰。展开/收起按钮改为竖排文字、圆角矩形透明描边样式，文字在上、箭头在下；展开时贴在排行榜左侧，收起时贴在屏幕右侧。

排行榜顶部显示居中的 `实时排行榜`，中间固定 8 个名次槽位。出价人数不足 8 人时，剩余槽位不显示用户名和头像，出价使用 `-` 占位。底部通过虚线分隔固定展示当前用户信息；当前用户未出价时，名次和出价均为 `-`。前三名使用带数字的金银铜牌，4 名及以后使用无背景、无边框的纯数字。第一名用户名使用金色，第一名出价比其他出价大约 20%，所有有效出价金额使用红色，并使用统一固定价格列居中对齐。排行榜面板高度按标题、8 个槽位、分隔线和当前用户栏贴合内容，避免当前用户栏下方出现多余空白。

排行榜动画由最近一次 `bid.accepted` 与随后的 `ranking.updated.items` 共同驱动。仅当位次发生变化或前 8 名发生进出时播放横条移动动画：前 8 名内用户升至第一时，横条从原位次浮起并移动到第一名；8 名外普通用户升至第一时，横条从虚线处分隔区域出现，同时第 8 名复用普通排行榜行样式，不作为放大的 ghost 渲染，按与 1-7 名相同的速度下移到虚拟第 9 名位置，并由前 8 名裁剪区隐藏虚线以下部分；当前用户在 8 名外或未出价时升至第一，则从底部当前用户栏复制横条起跳。当前用户固定信息栏始终固定在虚线下方，不参与 `is-exiting` 或下移动画；在当前用户升至第一的整段动画期间，固定信息栏持续保留旧位次和旧价格，直到动画最后一拍再与顶部横条同步切换到新位次和新价格。顶部目标行不再对整行重复挂 reveal，而是只对子节点做末帧显隐，并且目标第一名行不再叠加 `is-entering` 的上移动画，避免真实榜首先走到第二名轨道再在终帧闪到第一名；ghost 横条在尾帧前保持完全不透明，并直接复用榜首的金色用户名与放大价格样式，目标行内容直到终帧才接管显示，再在 `animationend` 后延后一帧清理 ghost，避免榜首收尾阶段出现半透明闪烁、文字虚化、样式跳变或最后一拍跳闪。其他用户动画约 0.5s，当前用户动画约 1s，当前用户横条放大幅度更强。若当前第一名再次出价但位次不变，不播放横条移动动画，只在出价数值处播放轻量滚动反馈。若动画未结束又收到新的出价，前端会直接结束旧动画并以最新排名快照开始新动画。排行榜价格列需要容纳第一名放大后的完整金额，避免小数位被截断。

直播间弹层生命周期从互斥 boolean 改为 `LiveSheetInstance[]` 实例状态机。每个弹层实例包含 `type / lotId / phase(opening|open|closing) / variant`，关闭时先进入 `closing` 并等待对应动画时长后卸载；打开时先挂载实例再播放进入动画。因此在拍品详情页点击 `去出价` 时，详情页关闭动画与快速出价弹层打开动画可以并行执行，避免中间空白或闪烁。

当前竞拍拍品小窗的显示时机也随状态机调整：当只有关闭中的弹层存在时，小窗会在关闭动画开始前恢复渲染，由弹层遮罩和面板遮挡；关闭动画结束后自然可见。若快速出价、拍品详情或竞拍清单仍处于 opening/open 状态，小窗仍保持隐藏，避免与窄屏底部操作区冲突。

## 2026-06-02 当前竞拍拍品小窗生命周期修正

直播间右下角当前竞拍拍品小窗现在由 `FloatingAuctionCardState` 统一管理，不再由“当前 activeLot 直接渲染”和“结束态 closing card”两套逻辑并行控制。状态包含：

- `mode`：`running / ended`。
- `phase`：`entering / visible / holding / leaving`。
- `auctionId / lot / state / ranking / enrolled` 快照，用于在动画期间保持展示稳定。

进入直播间时，如果当前没有 `RUNNING / EXTENDED` 拍品，不显示小窗；如果已有竞拍中拍品，则直接显示对应小窗。用户在直播间停留期间收到 `auction.started` 后，前端会按“同一直播间最多一个竞拍中拍品”的规则，将同房间其他 `RUNNING / EXTENDED` 本地状态收束为结束态，再把新拍品小窗以 `is-entering` 从底部 `竞拍清单` 按钮处竖直上弹。

收到 `auction.closed` 时，只有当前小窗实际可见且没有打开中的快速出价、拍品详情或竞拍清单弹层，才进入结束态。结束态倒计时区域显示 `END`，操作按钮显示禁用的 `竞拍结束`，保留约 5 秒后进入 `is-leaving` 并竖直下收入 `竞拍清单` 按钮。若 5 秒保留期间又收到新拍品 `auction.started`，旧小窗立即进入下收动画，动画结束后新小窗再上弹，避免两个小窗同时占据右下角。

小窗右上角新增无背景、无边框的 `×` 关闭按钮，aria 文案为 `auction.hideCurrentLot`。用户点击后只临时隐藏当前 `auctionId` 的小窗，后续同一拍品的倒计时或价格刷新不会重新唤起；下一件拍品开拍时会自动解除隐藏并正常弹出。小窗顶部缩略图使用独立媒体框，宽度与小窗一致，图片铺满并裁剪展示；媒体框保留整体圆角，顶部叠加从 50% 黑到透明的渐变遮罩。该遮罩专用于保持白色关闭按钮可见，关闭按钮贴近右上角并保持在遮罩范围内，减少对图片内容的破坏。

已登录直播页的竞拍状态 `placeholderData` 改为 memo 化，避免 `stateFromLot(activeLot)` 每次 render 都生成新对象并触发 React Query observer 与小窗派生 effect 的重复更新。

## 2026-06-03 直播预览进度承接与竞拍清单列表

首页直播推荐流进入正式直播间前，前端会读取当前激活预览视频元素的 `currentTime`，并通过 React Router location state 传入 `/live/:roomId`。该状态包含 `roomId`、`sourceUrl`、`currentTime` 和 `capturedAtMs`，只在房间和视频源 URL 匹配、时间值有效且快照未过期时应用。非首页入口、刷新直播间、跨视频源或无法读取时间时保持原有从头播放行为。

首页直播预览和正式直播间都会按 `roomId + sourceUrl` 在 `sessionStorage` 中持续记录当前视频播放进度。从首页预览进入正式直播间时，前端仍优先通过路由 state 传递即时进度快照；从正式直播间返回首页预览时，首页预览会读取同一缓存并恢复到离开直播间前的最新进度。正式直播间和首页预览在元素挂载、`loadedmetadata` 和 `canplay` 阶段都会尝试继续播放，但同一来源在同一次挂载中只应用一次进度快照，后续媒体事件只负责继续播放，避免真实浏览器连续触发 `canplay` 时把画面拉回旧时间点而看似暂停。数字人直播仅对 idle 视频源做同源进度承接，且同样只应用一次；speaking 视频仍由数字人状态控制，不做跨文件时间映射。

直播间新增统一声音开关，位置位于顶部右侧观众数旁边。该入口是观看端声音解锁能力，不是数字人播报控制面板。

## 2026-06-07 直播间竞拍氛围弹窗提醒

直播间新增 `LiveAuctionAlertLayer` 全局提醒层，用于在竞价关键节点提供更强的即时反馈。该层固定覆盖在直播间所有 UI 之上，包括快速出价、拍品详情和竞拍清单，但设置 `pointer-events: none`，因此不会拦截用户点击、关闭弹层、评论或出价操作。

提醒完全由现有实时事件派生，不新增 REST 或 WebSocket 协议字段：

- `bid.accepted` 且当前用户成为最高出价者：显示 `领先`。
- `bid.accepted` 且更新前当前用户是领先者、更新后由他人领先：显示 `被超越`。
- `timer.extended`：显示 `竞拍延时`，并展示更新后的倒计时。
- `auction.closed` 且当前用户未中标：显示 `竞拍结束`。
- `auction.closed` 且当前用户中标：显示 `竞拍成功`。

系统评论流仍会记录出价确认、延时和结束等消息，快速出价弹层内也继续展示后端反馈。全局提醒只承担即时视觉氛围，不替代业务记录或出价结果判断。提醒层同一时间只显示一个动画；当动画播放中收到新的竞拍提醒时，前端会立即清除旧提醒并播放最新提醒。倒计时提醒作为低优先级兜底，只在没有其他竞拍提醒时显示。旧的独立 `WinningCelebration` 渲染入口已由 `竞拍成功` 类型提醒替代，礼花和彩带效果归入新的全局提醒层，避免同一中标事件重复播放两套动画。

## 2026-06-07 倒计时提醒并入竞拍提醒层

直播间不再保留独立 `LiveCountdownPressureLayer`。当前正在竞拍的拍品进入最后关键秒数时，前端会派生一个 `kind=countdown` 的低优先级 `LiveAuctionAlert`，复用 `LiveAuctionAlertLayer` 展示倒计时氛围反馈。该提醒完全由当前拍品 `endTsMs`、本地 `now`、`timer.extended` 和 `auction.closed` 派生，不新增 REST 或 WebSocket 协议字段。

- 剩余时间大于 10 秒时不显示倒计时提醒。
- 剩余时间小于等于 10 秒时，倒计时提醒进入 `warning` 状态；小于等于 3 秒时进入 `critical` 强化态。
- 倒计时提醒优先级低于 `领先 / 被超越 / 竞拍延时 / 竞拍结束 / 竞拍成功`。当这些竞拍提醒正在显示时，倒计时提醒不会同时出现；高优先级提醒结束后，如拍品仍处于最后 10 秒，则倒计时提醒恢复显示。
- 收到 `timer.extended` 时仍会优先显示 `竞拍延时` 事件提醒；倒计时的 `extended` 重置态只作为低优先级补充，不与竞拍延时提醒同屏。
- 收到 `auction.closed` 后立即隐藏倒计时提醒，由 `竞拍结束` 或 `竞拍成功` 全局提醒接管。
- 倒计时提醒副标题在“提示文案 + 拍品标题”之间统一使用 `·` 分隔，避免 Demo 文案出现异常字符前缀。

当前竞拍拍品小窗的倒计时文本、快速出价弹层顶部倒计时和全局倒计时提醒复用同一套 `getCountdownPressurePhase` 阶段判断，避免不同位置对“最后 10 秒 / 最后 3 秒”的展示口径不一致。该功能不包含声音、震动或浏览器通知。

## 2026-06-09 直播间 30 秒倒计时光带

直播间新增 `LiveCountdownAmbientLayer` 装饰层，用于当前拍品处于 `RUNNING / EXTENDED` 且剩余时间小于等于 30 秒时提供持续倒计时氛围。该层与 `LiveAuctionAlertLayer` 独立，不新增可见文案，不接收触控事件，层级低于评论面板、当前竞拍拍品小窗和各类直播间弹层，因此不影响评论、出价、关闭弹层或拍品详情操作。

- 常态光效使用边缘光带与内侧细粒子组合，宽度为上一版常态的 150%，每侧 18 颗粒子持续从下往上运动；常态仍控制在屏幕左右边缘范围内，避免触及左侧评论开关、右侧竞拍清单、观众数量等控件。
- 光带从屏幕左右两侧底部开始显示，按 `(30s - remainMs) / 30s` 计算覆盖进度，并通过 100ms 级倒计时刷新保持匀速上升；倒计时归零时进度钳制为 100% 并进入结束脉冲/离场流程；收到 `bid.accepted`、`timer.extended` 或快照恢复导致 `endTsMs` 变化时，进度会按最新剩余时间重新计算。
- 色态由当前最高出价者派生：没有最高出价者或 `bidCount=0` 时为白色；他人领先时为红色；当前用户领先时为金色。
- 收到当前拍品的 `bid.accepted` 时，光带叠加一次更亮的出价脉冲，脉冲宽度为常态宽度的 2 倍，并在左右两侧脉冲光带范围内各生成 18 颗粒子；粒子从光带内层向脉冲外层散射，受 `.live-countdown-ambient-pulse-sparks` 容器裁剪，不会出现在脉冲光带范围之外。
- 倒计时归零时，光带进度保持 100%，立即播放一次结束脉冲并进入 `is-end-hold`；保持 1 秒后进入 `is-end-leaving`，两侧光带、光晕和常态粒子容器分别向屏幕外侧淡出。完成离场后，同一 `auctionId + endTsMs` 不会重复渲染光带；若后端通过延时事件或快照把 `endTsMs` 修正到未来，则清理结束态并重新按最新倒计时渲染。
- 收到 `auction.closed`、`auction.started` 切换新拍品、`live_session.lot_unmounted` 或 `live_session.lot_changed action=cancelled` 时会清理脉冲并隐藏旧光带；拍品取消后本地状态回到 `READY`，因此不会继续显示倒计时氛围。

最后 10 秒的居中 `kind=countdown` 提醒仍保留为低优先级全局提醒；30 秒光带负责持续背景氛围，二者不共享 DOM，也不新增 REST 或 WebSocket 协议字段。光带层级低于 `LIVE_SHEET_Z_INDEX_BASE=110` 的直播间弹层，弹层打开时会覆盖光效。

## 2026-06-12 收尾巡检：路由过渡超时修复

本轮全局烟测在移动端浏览器中复现了一个真实运行时问题：首页底部 Tab 从“首页”切换到“发现”或“我的”时，页面虽然最终可以完成跳转，但控制台会报出 `Transition was aborted because of timeout in DOM update`。根因是前端手动调用 `document.startViewTransition(...)` 包裹 `navigate(...)`，而应用同时启用了 React Router 的 `future.v7_startTransition`，导致路由 DOM 更新没有在 View Transition 期待的同步窗口内提交。

修复方式是删除手写的 `document.startViewTransition` 包装，统一改为通过 React Router 自身的 `navigate(..., { viewTransition: true, flushSync: true })` 选项发起路由切换，让 Router 在支持 View Transition 的浏览器中自行处理同步提交边界。这样既保留页面切换动画能力，也消除了路由切换时的控制台超时错误。

本轮补充了 `src/router/navigation.ts` 与 `src/router/navigation.test.ts`，将该路由切换策略收敛为独立内部助手并增加回归覆盖；同时在浏览器烟测中重新验证了首页、发现、我的和直播间入口，未再出现新的 `Transition was aborted because of timeout in DOM update` 错误。

## 2026-06-13 全量巡检补修：关注、支付回跳与结果页遮挡

本轮逐页面浏览器巡检在真实交互链路中补出了三类实现层问题，并已同步修复：

- 直播间关注状态与 `/following` 列表曾存在刷新断层：直播间头部按钮可以切换到“已关注”，但重新进入关注列表时仍可能为空。根因是本地 Demo API 只在内存里维护 `followedMerchantIds`，整页重载后状态丢失。当前实现已将该集合持久化到 `localStorage`，并在 `DemoApiClient` 初始化时回填，保证 Demo 模式下关注关系与“我的关注”列表一致。
